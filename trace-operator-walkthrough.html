Which dashboard am I using?

Original Streamlit demo

Local simulator with an SQLite case store, a reference photo form, simulated search stages, candidate clips, and PDF reports.

React demo mode

The default React view follows the Streamlit simulator. Sign in with operator / trace-demo, then find a saved case, create a sample case, or upload a photo in New case.

React connected mode

Open the dashboard URL with ?controls for this separate workspace. It uses the Python Controls API for sign-in and case actions. Your local test server uses in-memory fixtures and offers api-case. Its changes reset on server restart.

Walk through a case in React

Streamlit workflow in the default React view

Run npm run dev in frontend/. Sign in with operator / trace-demo. In New case, choose a photo from your files, rotate or crop it if needed, select a camera by name, and enter the last-known date and time. After submitting, select Open case. In Current case, the Candidates, Route, and Case details tabs guide review through the simulated search stages. The camera wall plays sample warehouse recordings from the team repository. The review queue displays the simulator’s case candidates, with three-second warehouse excerpts available in candidate details. Case details includes the PDF report and the original close and delete actions.

Separate Controls-connected workspace

  1. Connect and open a case. Run the frontend and, in a second Terminal window in frontend/, start the loopback fixture using the setup in the frontend README. Once it says Uvicorn is running on port 8080, select Connect to Controls. Use operator / trace-local-demo for that local server. Open Cases and select api-case. Team deployments use their own backend accounts.
  2. Start another case. In connected mode, an account with creation permission can choose Cases → New case. Choose a reference photo, preview or adjust it, then select the last-known camera and time in KST. The dashboard generates case and target IDs, uses the configured site and version, and submits the photo to Controls before creating the case. The dashboard uses the last-known time as the start and submission time as the end of the search window.
  3. Inspect cameras and the route. Choose Cameras to expand a tile or Route map to inspect the path and zoom. The four demo stills depict a fictional entrance, corridor, parking level, and service exit. A connected case shows the latest snapshot if Controls publishes one. An empty camera panel can occur with the local test case. Its route and candidates can still be available.
  4. Review a candidate. Open an item in Review queue to see the camera, observed times, and appearance score. Open Candidate clip when Controls has published one. Use Confirm match or Reject when available. Scores represent visual similarity and support human review. Switch to All to see candidates outside the pending queue.
  5. Check activity and finish. Search activity displays job counts, coverage gaps, and errors reported by the backend. Use Case actions → Close search when finished. In connected mode, request clip export when permitted. Open or download the merged MP4 under Case recordings when it is ready. Deletion also depends on account permission and case state.

How this fits the proposal

The case form, ranked candidate review, probable route, and evidence export action reflect the proposed operator workflow. Person re-identification, actual footage search, routing, and clip preservation depend on the deployed backend and its workers.

The separate Controls-connected workspace still needs direct reference-photo upload and playback of the preserved clips. The default simulator workflow already supports photo upload. The local test server demonstrates Controls requests with sample results.
